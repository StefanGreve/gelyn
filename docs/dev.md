# Development

[TOC]

The repository root carries a `Makefile` that collects the commands on this page into named targets.

## Building from Source

### Make Targets

Every target below is phony, and the recipes are silenced; `make V=1 <target>` echoes them instead.

| Target         | Runs                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| `make setup`   | Local tools, the `git` hooks, the package restore, and the enforced `git` config.  |
| `make build`   | `dotnet build` in Release, without restoring.                                      |
| `make test`    | Depends on `build`, then `dotnet test` in Release without rebuilding.              |
| `make publish` | `dotnet publish` of `src/Gelyn` for `RID`.                                         |
| `make install` | Packs `src/Gelyn` for `RID` and installs it as a global tool, replacing any copy.  |
| `make gelyn`   | Publishes, then builds or serves the site named by `project`.                      |
| `make lint`    | `dotnet format` across the solution.                                               |
| `make clean`   | `dotnet clean` in both configurations, removes the global tool, clears the screen. |

> [!NOTE]
> `make setup` is the only target that is required, and it is required once after cloning.

On Windows, the recipes run under `cmd.exe` regardless of the shell that invokes `make`, so cmd, PowerShell, and
Git Bash behave alike.

What a target does depends on the arguments below. Each is appended to the command, as
`make <target> <argument>=<value>`:

| Argument            | Read by                       | Default                | Effect                                                   |
| ------------------- | ----------------------------- | ---------------------- | -------------------------------------------------------- |
| `project=<dir>`     | `gelyn`                       | `docs`                 | Directory holding the site's `gelyn.json`                |
| `serve=true`        | `gelyn`                       | unset                  | Serves the site and rebuilds on every change             |
| `refresh=<seconds>` | `gelyn`                       | unset                  | Seconds between page reloads while serving               |
| `RID=<rid>`         | `publish`, `install`, `gelyn` | host platform and arch | [Runtime identifier][known-rids] the binary is built for |

Each site in this repository builds through the `gelyn` target:

```sh
make gelyn                                   # build docs/
make gelyn project=example                   # build example/
make gelyn project=docs serve=true           # serve it, rebuilding whenever a file changes
make gelyn project=docs serve=true refresh=2 # and reload the page every two seconds
```

The target publishes before it runs, so a site is always generated by the current source.

### Building by Hand

Install the development dependencies and register the `git` hooks:

```sh
dotnet tool restore
dotnet tool run husky install
```

Build and run this project:

```sh
dotnet build
dotnet run --project src/Gelyn -- <command>     # e.g. build
```

Run the test suite:

```sh
dotnet test
```

Tests use [`TUnit`][tunit], which runs on [`Microsoft.Testing.Platform`][mtp]; its [documentation][tunit-docs]
covers the authoring conventions this suite follows.
A [`Husky.Net`][husky] `pre-push` hook runs the same suite before every push.

To use the tool locally, publish it and link the resulting binary onto your `PATH`:

```sh
dotnet publish src/Gelyn -r osx-arm64
ln -sf "$PWD/src/Gelyn/bin/Release/net10.0/osx-arm64/publish/gelyn" ~/.local/bin/gelyn
```

`PublishAot` makes that a standalone executable, so the link is made once and every later `dotnet publish`
updates the command in place. Then invoke it by its command name (`gelyn`).

> [!TIP]
> Use one of the known [RIDs][known-rids] in place of `osx-arm64`; `Gelyn.csproj` lists the set this project
> targets. Native AOT cannot cross-compile between operating systems, so each one is built on its own.

Packing and installing as a global tool works differently: it rehearses what a consumer gets, including
the runtime-specific package layout that the publish output alone does not cover.

```sh
dotnet pack && dotnet pack -r osx-arm64
dotnet tool install --global Gelyn --prerelease
```

`make install` runs these steps for the host's `RID`. It first deletes the packages an earlier run left in
`artifacts/nupkg`, so that `--prerelease` cannot pick a higher version built from a later commit. It also
uninstalls the tool before installing it, because MinVer gives every build of one commit the same version, and
an installed copy of that version would otherwise count as up to date.

> [!TIP]
> The [tab completion](cli.md#tab-completion) shim asks `dotnet-suggest` which commands to complete once, when
> the shell starts, so a shell that was open before the first install does not complete `gelyn`. Open a new
> shell, or reload the profile in PowerShell with `. $PROFILE.CurrentUserAllHosts`. `make install` cannot do
> this for you, because its recipes run in a child process that cannot change the shell that started `make`.

> [!NOTE]
> A plain `dotnet pack` emits only the pointer package listing the per-architecture ones, so the matching RID
> has to be packed as well. `Gelyn` resolves as a package id rather than a path, so `nuget.config` declares
> `artifacts/nupkg` as the `local` source and maps `Gelyn*` to it.

### The Configuration Schema

`gelyn.schema.json` is generated and never edited by hand. After every build of the solution, `src/Gelyn.Schema`
exports it from `SiteOptions` through [`JsonSchemaExporter`][extract-schema] and rewrites the file when its
content changed. Each part of the schema has one source:

| Part                                                  | Source                                                                           |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| Keys, types, `null`, `format`, `additionalProperties` | The options types in `src/Gelyn/Model/Options`                                   |
| `description`                                         | The `<summary>` of each property                                                 |
| `examples`                                            | Each `<example>`, as written for a string setting and as JSON for any other      |
| `required`, `pattern`, `minimum`, `maximum`           | `[Required]`, `[RegularExpression]` and `[Range]`                                |
| `uniqueItems`                                         | `[UniqueItems]` from `Gelyn.Attributes`                                          |
| `minLength`                                           | Every string that excludes `null`, as `SiteOptionsValidator` rejects a blank one |
| `default`                                             | The initializers of `SiteOptions`                                                |
| The `enum` of `Theme`                                 | The stylesheets and scripts in the theme folder                                  |

The build fails when a property has no summary or a setting has no example, so the schema never ships without
either.

Commit the regenerated file with the change that caused it. A CI build compares the file instead of writing it,
the way restore treats a stale lock file, and fails when the two differ. The `pre-push` hook refuses a push whose
commit lacks the regenerated file. `git push --no-verify` skips that hook, but not the check in CI. A merge
conflict in the file is resolved by building the solution, not by editing it.

## The SDK Pin

`global.json` names the exact SDK this repository builds with and sets `rollForward` to [`disable`][global-json],
which "doesn't roll forward; an exact match is required". Every `dotnet` command fails until that SDK is
installed, and the failure carries the `errorMessage` the same file declares.

The strictness is deliberate, and Native AOT is the reason for it. `PublishAot` and trimming inject
`Microsoft.DotNet.ILCompiler` and `Microsoft.NET.ILLink.Tasks` as implicit package references whose versions
the SDK alone chooses, so the SDK version reaches the lock file that `Gelyn.csproj` maintains through
`RestorePackagesWithLockFile`. The `global.json` reference pairs the two: when you use
[package lock files][lock-files], set `rollForward` to `disable` so the SDK version and the dependency graph
stay in lockstep. The pin also fixes the compiler that emits the binary, ILC being what turns the IL into
machine code.

A bump is therefore two files. Moving the pin moves both of those packages and every
`runtime.<rid>.Microsoft.DotNet.ILCompiler` entry with them, so run `dotnet restore` after editing
`global.json` and commit the regenerated `src/Gelyn/packages.lock.json` beside it. CI installs the pinned SDK
by itself through `global-json-file`, and it never regenerates the lock file, so a commit moving the pin alone
fails restore with `NU1004`.

On macOS, `scripts/install-dotnet-sdk-macos.sh` installs a pinned SDK and removes the one it replaces:

```sh
scripts/install-dotnet-sdk-macos.sh --install-version=10.0.403 --remove-version=10.0.401
```

It downloads the [official `.pkg`][dotnet-download] for that version, verifies that Microsoft signed it,
installs it, and deletes the older SDK along with its `pkgutil` receipt. Omit `--install-version` to take the
version from `global.json`, and pass `--dry-run` to print every step without running any of it.

> [!NOTE]
> `dotnet-install.sh` overwrites the shared host at `/usr/local/share/dotnet/dotnet` in place, which can
> leave macOS killing every `dotnet` invocation with `SIGKILL` over a stale code signature. The `.pkg`
> replaces it cleanly, and Homebrew's `dotnet-sdk` cask runs that same `.pkg` when the latest version will
> do. Linux validates no such signature, so `dotnet-install.sh --jsonfile global.json` is the route there and
> the script refuses to run.

On Windows, `winget` installs and removes one exact SDK version, so the script has no counterpart there:

```powershell
winget install -e --id Microsoft.DotNet.SDK.10 -v "10.0.403"
winget uninstall -e --id Microsoft.DotNet.SDK.10 -v "10.0.401"
```

Without `-v`, [`winget uninstall`][winget-uninstall] removes "the highest versioned application", which is the
pinned SDK whenever the pin is the newest one installed.

## Versioning

No project file carries a version number. [MinVer][minver] reads the nearest reachable git tag at build time
and stamps it onto the assembly, which is what `gelyn --version` prints and what the page footer renders, so
a release is cut by tagging a commit. Tags are prefixed with `v`, and `make setup` configures
`tag.gpgsign`, so they are annotated and signed:

```sh
git tag -m 'Gelyn 0.1.0' v0.1.0
git push origin v0.1.0
```

A tagged commit builds as the tag itself. Between tags the commit height is appended, which keeps every build
uniquely versioned and correctly ordered: three commits past `v0.1.0-alpha.1` build as `0.1.0-alpha.1.3`, and
three commits past a stable `v0.1.0` build as `0.1.1-alpha.0.3`, because MinVer increments the patch number
and adds its default pre-release identifiers once a tag is no longer a pre-release.

With no reachable tag at all the version falls back to `0.0.0-alpha.0` plus the height, which is the one
failure mode worth knowing. A shallow clone reaches no tag, so the CI checkouts in `dotnet-build.yml` and
`gelyn-build.yml` set `fetch-depth: 0`; a local clone made with `--depth` reports `0.0.0-alpha.0.N` for the
same reason, and `git fetch --unshallow --tags` restores it.

`AssemblyVersion` is pinned to `<major>.<minor>.0.0` by the `PatchAssemblyVersion` target in
`Directory.Build.targets` instead of MinVer's own `<major>.0.0.0`. Before 1.0.0 the minor number carries the
breaking changes, so it belongs in the binding identity while the patch number does not; the target comes out
once 1.0.0 ships.

## Notes on Deployment

`gelyn-build.yml` publishes `docs/` to GitHub Pages once a `Build` run on `master` succeeds. Besides the rendered
pages, the site carries files that `gelyn build` doesn't produce: `schema.json`, which is a copy of
`gelyn.schema.json`, and `llms.txt` with `llms-full.txt` for agents. The workflow writes them after the
build, because the build reconciles `_docs` and deletes every file it didn't publish itself.

`scripts/generate-llms-txt.sh` writes the two agent files. `llms.txt` is the index the [llms.txt
proposal][llms-txt] specifies, and `llms-full.txt` carries the pages it lists as one Markdown file, so an agent
can read the documentation in a single request. Neither file is checked in, because the script derives both
from the pages and `docs/gelyn.json` on every run.

To check the output locally, build the site first, then run the script against it:

```sh
make gelyn
bash scripts/generate-llms-txt.sh -b https://stefangreve.github.io/gelyn -r https://github.com/StefanGreve/gelyn
```

`--output` writes to another directory, which has to exist already. The script reads `docs/gelyn.json` with
[`jq`][jq], which Git Bash doesn't include, so install it once on Windows:

```powershell
winget install -e --id jqlang.jq
```
