# Development

The repository root carries a `Makefile` that collects the commands on this page into named targets. Run
`make setup` once after cloning.

## Building from Source

Install the development dependencies and register the `git` hooks:

```sh
dotnet tool restore
dotnet tool run husky install
```

Build and run this project:

```sh
dotnet build
dotnet run --project src/Gelyn -- <command>     # e.g. build
```

Run the test suite:

```sh
dotnet test
```

Tests use [`TUnit`][tunit], which runs on [`Microsoft.Testing.Platform`][mtp]; its [documentation][tunit-docs]
covers the authoring conventions this suite follows.
A [`Husky.Net`][husky] `pre-push` hook runs the same suite before every push.

To use the tool locally, publish it and link the resulting binary onto your `PATH`:

```sh
dotnet publish src/Gelyn -r osx-arm64
ln -sf "$PWD/src/Gelyn/bin/Release/net10.0/osx-arm64/publish/gelyn" ~/.local/bin/gelyn
```

`PublishAot` makes that a standalone executable, so the link is made once and every later `dotnet publish`
updates the command in place. Then invoke it by its command name (`gelyn`).

> [!TIP]
> Use one of the known [RIDs][known-rids] in place of `osx-arm64`; `Gelyn.csproj` lists the set this project
> targets. Native AOT cannot cross-compile between operating systems, so each one is built on its own.

Either of the two sites in this repository builds through the `gelyn` target, where `project` names the
directory that carries the site's `gelyn.json` and defaults to `docs`:

```sh
make gelyn                                   # build docs/
make gelyn project=example                   # build example/
make gelyn project=docs serve=true           # serve it, rebuilding whenever a file changes
make gelyn project=docs serve=true refresh=2 # and reload the page every two seconds
```

The target publishes before it runs, so a site is always generated by the current source.

Packing and installing as a global tool works differently: it rehearses what a consumer gets, including
the runtime-specific package layout that the publish output alone does not cover.

```sh
dotnet pack && dotnet pack -r osx-arm64
dotnet tool install --global Gelyn --prerelease
```

> [!NOTE]
> A plain `dotnet pack` emits only the pointer package listing the per-architecture ones, so the matching RID
> has to be packed as well. `Gelyn` resolves as a package id rather than a path, so `nuget.config` declares
> `artifacts/nupkg` as the `local` source and maps `Gelyn*` to it.

## Versioning

No project file carries a version number. [MinVer][minver] reads the nearest reachable git tag at build time
and stamps it onto the assembly, which is what `gelyn --version` prints and what the page footer renders, so
a release is cut by tagging a commit. Tags are prefixed with `v`, and `make setup` configures
`tag.gpgsign`, so they are annotated and signed:

```sh
git tag -m 'Gelyn 0.1.0' v0.1.0
git push origin v0.1.0
```

A tagged commit builds as the tag itself. Between tags the commit height is appended, which keeps every build
uniquely versioned and correctly ordered: three commits past `v0.1.0-alpha.1` build as `0.1.0-alpha.1.3`, and
three commits past a stable `v0.1.0` build as `0.1.1-alpha.0.3`, because MinVer increments the patch number
and adds its default pre-release identifiers once a tag is no longer a pre-release.

With no reachable tag at all the version falls back to `0.0.0-alpha.0` plus the height, which is the one
failure mode worth knowing. A shallow clone reaches no tag, so the CI checkouts in `dotnet-build.yml` and
`gelyn-build.yml` set `fetch-depth: 0`; a local clone made with `--depth` reports `0.0.0-alpha.0.N` for the
same reason, and `git fetch --unshallow --tags` restores it.

`AssemblyVersion` is pinned to `<major>.<minor>.0.0` by the `PatchAssemblyVersion` target in
`Directory.Build.targets` instead of MinVer's own `<major>.0.0.0`. Before 1.0.0 the minor number carries the
breaking changes, so it belongs in the binding identity while the patch number does not; the target comes out
once 1.0.0 ships.
